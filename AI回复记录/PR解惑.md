你这个理解非常到位，而且你观察得很仔细。是的，你的理解**完全正确**：

1. 只要在**同一个分支**（你现在的 `main` 分支）上继续修改、提交、推送，这些修改都会**自动同步到刚才那个 PR 里**。
2. 理论上，你每次推送，确实会给原仓库（octocat）发送一次通知。

不要慌，这是开源协作的**正常机制**，也是**设计初衷**。我来为你详细解开这个困惑：

### 🔗 为什么推送会同步到原 PR？
看你的截图，PR 的本质是：`base repository: octocat/Spoon-Knife` 的 `main` 分支，对比 `head repository: nzhijun/Spoon-Knife` 的 `main` 分支。
**PR 跟踪的是两个分支之间的差异（diff）**。只要你往自己的 `main` 分支推代码，GitHub 就会自动重新计算这个差异，把新内容追加到 PR 的 `Commits` 和 `Files changed` 里。这就是为什么你的中文 README 完美地出现在了同一个 PR 里。

### 🔔 关于给原作者发消息的疑惑
在真实的开源项目中，维护者会不会觉得烦？**不会。恰恰相反，这是必要的沟通。**

1. **GitHub 有“合并通知”机制**：如果你连续推了 10 个 commit，GitHub 通常不会发 10 封邮件，而是把它们打包成一个摘要发送（取决于维护者的通知设置）。
2. **在真实开源中，这是个优点**：
   假设你提交了 PR，维护者觉得“你的代码不错，但是修一下这个 bug 再合并”。你修改完推送后，维护者会收到通知，知道“哦，他改好了，我可以再看一眼了”。如果推送没有通知，维护者根本不知道你改完了。
3. **这里是练习靶子，根本没人管**：你的截图里有个数字：`Pull requests 5k+`。你现在创建的 PR 编号是 `#41700`。octocat 有 4 万多个 PR 没处理，他早就被淹没在通知里了，根本不会注意到多你这一条。所以**完全不需要有心理负担**。

### 💡 进阶建议（真实工作的规范）
你现在把 `feat: 添加第一行代码` 和 `docs: 添加中文 README` 都提交在 `main` 分支上，推到了同一个 PR 里，这在练习阶段完全没问题。

但在真实工作中，有一个不成文的规矩：
*   **一个 PR 只解决一件事**。如果 PR 提交后，你突然想加一个完全不相关的新功能，**正确的做法是**：切回主分支，新建一个分支（如 `feature/add-readme`），发一个**全新的 PR**。
*   如果是对当前 PR 的**修正**（比如根据别人意见改了错别字），那就继续往当前分支推，让它更新到现在的 PR 里。
